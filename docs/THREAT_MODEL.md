Status: draft v3, 2026-10-19. v2 added the simulation evidence (`docs/SIMULATION_RESULTS.md`),
marked which mitigations exist in code, and added threats T19–T23 surfaced while building.
v3 records encryption at rest in the web app (T9, T22) and the 1:1 Match protocol in
`packages/match` (T2, T4, T5, T10, T15), and adds T24–T26.
v4 records the Circles prototype in `packages/circles` (T3, T19, T20; design in `docs/CIRCLES.md`), on-device
moderation in `packages/moderation` (T18), and the native shells in `apps/mobile` and `apps/desktop`, and adds
T27–T33.
Companion to `docs/DESIGN.md`. Source IDs (A12, N1, …) refer to the Sources list in DESIGN.md.

## What we protect

| Asset | Where it lives | Why it matters |
|---|---|---|
| Watch / endorsement history | user device only | reveals politics, health, sexuality, religion; legally sensitive (VPPA, GDPR Art. 9) |
| Taste sketches | sent to matches, E2E | a subset of the above |
| **Match graph** (who matches whom) | the two endpoints; relays see metadata | maps communities of like-minded people; a dissident list |
| Circle membership | circle members; relays see metadata | same as above, but for groups |
| Identity keys | user device | impersonation, reading future sketches |
| Feed integrity | user device | what people actually see; the whole point of the project |
| Creator content and reach | instances, mirrors | creators' livelihood |
| Creator analytics | aggregation servers | must not become a viewer tracker |

## Adversaries

| Adversary | Capability | Wants |
|---|---|---|
| A1. Curious match | sees your sketch | learn more about you |
| A2. Abusive match (partner, family, employer) | can coerce you to match; may have your unlocked phone | monitor you |
| A3. Prober | sends many PSI previews or match requests | learn if *you* watched video X |
| A4. Sybil / bot operator, payola buyer | many keys, scripted accounts | push content into feeds |
| A5. Malicious feed-recipe author | ships code users run | exfiltrate history; manipulate ranking |
| A6. Malicious relay | stores and forwards events | metadata, censorship, replay |
| A7. Instance admin, voluntary or compelled | runs a PeerTube instance | account data, IPs, takedowns |
| A8. Network observer / state | ISP-level visibility, legal compulsion, app-store pressure | identify viewers and match graphs; block the app |
| A9. Device seizure / forensics | physical access | local plaintext history |
| A10. Supply-chain attacker | compromises our release or a dependency | everything, for every user |

## Threats and decisions

Severity is the impact if exploited, given the current design. Status shows whether a
mitigation is **decided**, needs an **option to be chosen**, or still needs **research**, and
whether it is **implemented** in code. Paths are relative to the repo root; "core" means
`packages/core/src`, "web" means `apps/web/src`, "match" means `packages/match/src`.
`packages/match` is a prototype: it has no network relay I/O, is not wired into the web app, and is not audited.
"circles" means `packages/circles/src`: also a prototype (in-memory relay only, not wired into the web app, not audited).

| T1 | A feed recipe exfiltrates history over the network | A5 | Critical | Recipes are declarative only (weights, filters); the client evaluates them over candidate lists, never raw history. Unknown keys rejected; 16 KiB limit checked before parsing | Decided (D1). **Implemented:** core `recipe.ts` (`parseRecipe`, `parseRecipeJson`), core `validate.ts`; web recipe import goes through `parseRecipeJson` |
| T2 | PSI preview used as an oracle ("did you watch X?") | A3 | High | **Changed after simulation (Exp 4).** The target learns the PSI-cardinality and releases only a **noised value: discrete Laplace ε = 0.5, floor 5** ("<5" below it), shown as coarse buckets. **At most 8 accepted previews per target per rolling year, from all requesters**, counted on the target's device. The target must accept every preview; per-pair (1/week) and per-requester (5/week) limits stay. The ≥ 20-item minimum set size stays as hygiene only: **it is not a defense**, because a prober pads probes with its own never-watched uploads. Evidence: one exact preview answers the question with certainty; a floor or buckets alone fail once the prober knows 4 of the target's items; per-pair limits don't stop Sybils (50 Sybils at 10% acceptance need 1 week). With floor 5 + ε = 0.5 and 8 previews, prober AUC ≤ 0.83 and 0% of positives inferred at ≥ 90% confidence, even with 4 known items [A10] | Decided. **Policy implemented:** core `preview.ts` (`noisyPreviewCardinality`, `previewBudgetRemaining`, `respondToPreview` refusing with `target-budget`; ε, floor and budget can't be loosened; `previewDisplay` maps a received value to the same buckets). **Protocol implemented (prototype):** match `state.ts`: every preview needs the target's acceptance (`respondToMatchPreview`); a spent budget is sent as an ordinary decline (`accept: false`), so the requester can't tell it from a refusal; the noise is applied on the target's device inside `completeTargetPreview`, so only the noised value reaches the outbox (`preview-result`: `floor`, `belowFloor`, `value`); the requester shows the bucket label via `previewDisplay`. Match `psi.ts`: PSI roles are flipped so only the target (PSI client) learns \|A∩B\|; OpenMined PSI runs cardinality-only, refuses requests that ask to reveal the intersection, and both sets are padded to 128 items. **Limits:** the budget is counted only on the target's own device; the requester's `setSize` is self-reported (hygiene only); OpenMined PSI is unaudited (T26) |
| T3 | Circle output reveals individual picks (k too small, subtraction, round-to-round diffs) | A1 | High | **k ≥ 8 hard floor, 12–30 recommended**; reveal threshold on the *noised* count, **t = 3 for k = 8–15, t = 4 for k ≥ 16**; **ε = 1** discrete-Laplace noise per item per epoch [A13]; **sticky noise** (same draw per item per epoch); **epoch freeze** (each MLS epoch released once, never recomputed after a membership change); **picks only, never counts**. Evidence (Exp 3): a single release to one insider leaks little even at k = 5; colluders subtracting their inputs reveal 3–39% of a member's endorsements without noise and none at ≥ 90% confidence with ε ≤ 2; sticky noise without a freeze still lets membership differencing expose 15–22% at k = 8–12; showing noisy counts exposes 49–94% whatever ε is. k = 12, t = 3, ε = 1 keeps 86% recall / 77% precision of group picks | Decided. **Output policy implemented:** core `circle.ts` (`CIRCLE_MIN_MEMBERS`, `revealThresholdFor`, `releaseCircleEpoch`, `circlePicks`; `noisedCount` deprecated and never populated). **Prototype (`packages/circles`):** MLS transport via marmot-ts; pairwise-masked secure aggregation over a public candidate list (circles `masking.ts`, `round.ts`); distributed Pólya noise (T19); core's policy applied to the aggregate with epoch freeze and ledger (circles `policy.ts` `releaseAggregatedEpoch`); a failed round voids its epoch permanently, so a withheld vector can never yield a second output. **Caveat, changes Exp 3's collusion result:** with distributed noise, ε = 1 holds only against up to c colluders (default ⌈m/3⌉ − 1, 3 at m = 12). Exp 3's "collude" scenario (everyone but the target colludes) kept 0% at conf90 with a trusted seed; **under distributed noise it does not hold**, because the target is protected only by its own small share (CIRCLES.md §5). Every device also sees the noised counts while summing; "picks only" is enforced by honest clients, not cryptography. **Research:** multi-epoch DP accounting; dropout recovery (any dropout after the key phase voids the epoch) |

| T5 | Relay metadata reveals the match graph | A6, A8 | High | NIP-17 gift-wrap hides the sender [N1]; random relay selection; fixed-size padded sketches (8,192 / 15,872 bytes; 31,232 over MLS only) on a fixed schedule; Oblivious HTTP to relays [S2]; mixnet transport as an option later [S3]. Marmot (MLS over Nostr) sends Nostr pubkeys and group tags in plaintext, so relays and observers can track circle membership, timing and volume (Least Authority review, Nov 2025) [N3] | Decided (Tor/mixnet: later). **Padding implemented:** core `sketch.ts` (buckets, item and byte padding). **Match (prototype):** match `wrap.ts` sends every message as a NIP-59 gift wrap (one-time wrap key, timestamps jittered up to 2 days, tags `p` and `expiration` only); match `messages.ts` pads every control message to exactly 8,192 bytes, the size of a 64-bucket sketch, so relays see two wrap sizes (19,649 and 33,305 bytes); `dueSketches` gives a fixed weekly schedule. **Not implemented:** random inbox-relay selection, OHTTP, cover traffic for user-timed handshakes; a target's identity key still receives first-contact wraps |

| T7 | Sybil accounts push content via second-degree propagation or public taste lists | A4 | High | Second degree only through opted-in matches; **row-normalized personalized trust walk, decay 0.3, 2 hops, per-node cap 0.05 of the viewer's trust mass** [A14][A15][A23]; **each taste list contributes at most 2 items per feed**; **list weight from track record, not subscriber count**; sponsored flag on list entries. ## Decisions that are yours

**D1. Feed-recipe safety (T1). DECIDED 2026-10-19: declarative recipes only (JSON weights and filters). No code execution.** Implemented in `packages/core/src/recipe.ts`.

| Option | Pros | Cons |
|---|---|---|
| Declarative recipes only (JSON weights + filters) | simplest to audit; no code execution | limits what community recipes can do |
| WASM sandbox, no I/O | expressive; still can't exfiltrate | sandbox escapes are possible; bigger attack surface; harder review |
| Both: declarative by default, WASM behind a warning | flexible | two systems to maintain |

**D2. Coercion handling (T4). DECIDED 2026-10-19: quiet pause plus per-match exclusions (baseline).** The pause re-sends the same items in a fresh envelope, so the sketch keeps arriving on schedule; the remaining tell is only that its content stops changing. Implemented in `packages/core/src/sketch.ts`.

| Option | Pros | Cons |
|---|---|---|
| Silent pause + exclusions (baseline) | simple; plausible | the abuser may notice the sketch stops changing |
| Decoy mode: send a plausible but stale or partial sketch | stronger plausible deniability | if discovered, users are endangered; hard to do well |
| Baseline + safety-planning copy, done with an advocacy org | grounded in real abuse cases | slower; needs partners |

**D3. Second aggregator for creator analytics (T14). Open: Q2 (country stats), the helper operator, and the EU ePrivacy question. See `docs/ANALYTICS.md`.

| Option | Pros | Cons |

## Process

1. **Outside review.** Review this model with 1–2 outside privacy engineers. Not done yet. Code now exists for the v1 tiers, the Match/Circle policy layers and the 1:1 Match protocol core (`packages/match`, no network I/O yet), so this should happen before Match talks to real relays.
2. **Prefer audited primitives; never roll our own crypto.** Audit status as of 2026-10-19 (see `docs/OSS_STACK.md` and the research notes):
   - **Marmot / MLS over Nostr:** Least Authority reviewed the Marmot protocol (summary report 7 Nov 2025; MIPs 00–04, MIP-05 excluded as incomplete). It found no existing threat model and recommended one, plus careful separation of the MLS extractor key used for NIP-44 encryption, and noted plaintext pubkeys and group tags (T5). Least Authority also audited whitenoise-rs (final report 1 April 2026). Whether MDK itself was in scope is unconfirmed. marmot-ts is alpha and unaudited, so use it for the prototype only.
   - **NIP-44:** Cure53 audited the NIP-44 spec and the paulmillr/nip44 JS/TS, Go and Rust implementations (Nov–Dec 2023): 10 findings, NOS-01-001 to NOS-01-010, none exploitable. Medium: missing range checks (NOS-01-005) and no forward secrecy (NOS-01-006). Low: HMAC timing (NOS-01-004) and no signing/encryption key separation (NOS-01-007). NOS-01-001 (twist attacks) is informational. Per its maintainer, only the JS implementation was audited in its final form. Confirm that nostr-tools ships the same code.
   - **OpenMined PSI: no audit**, and its README states no security model. `packages/match` uses `@openmined/psi.js` 2.0.6 for previews (T26). Commission one, or budget for it in the pre-launch audit.
   - **Our own code:** `keyedRng` and its SHA-256 (T20) must be replaced by audited code before Circles ship. `packages/circles` already avoids it, but its secure aggregation, distributed noise and app-level MLS guards are our own composition of standard primitives and need review (CIRCLES.md §9).
   - **marmot-ts / ts-mls:** alpha and unaudited; `packages/circles` runs marmot-ts 0.5.1 with an overridden ts-mls (T27, T28).
3. **Before Match launches:** an external security audit of the Match and Circle protocols and the client. Cure53, Least Authority and Trail of Bits have audited comparable systems.
4. **Simulate T3, T2 and T7. DONE (first pass, 2026-10-19):** `docs/SIMULATION_RESULTS.md`, harness in `sim/`. Synthetic data; it sets parameters and compares mechanisms, not absolute risk. Not simulated: relay metadata (T5), multi-epoch Circle accounting, secure-aggregation dropouts, adaptive Sybils, real cryptography.
5. **Ongoing:**

   - a bug bounty after launch

   - telemetry only through private aggregation (no other analytics SDKs)
6. **Incident response:** a key-revocation broadcast, forced sketch-epoch rotation, and a user notice template.

## Known residual risks

These can't be engineered away. Say them plainly in the UI.

- A match can keep and leak whatever you sent them.
- Anyone recommended a video "because of" a match learns that the match endorsed it.
- A match who is a Sybil reaches you directly; the trust walk only stops it spreading further.
- Even with noise and a budget, previews leak a little: after 8 accepted previews a well-informed prober's AUC can reach about 0.83.
- Relays still see that *some* encrypted traffic flows, and when, unless a mixnet is used.
- A compelled app-store removal will cut off casual users even if sideloading works.
